# AI 自主迭代规则

> 本文档定义 AI 在自主开发 AgentForge 项目时必须遵守的规则。违反规则可能导致代码质量问题。

---

## 1. 每次开发前必须读取的文档

### 必读文档（按优先级）

| 优先级 | 文档 | 何时读 | 原因 |
|--------|------|--------|------|
| 1 | `task-backlog-v0.1.md` | 领取每个任务前 | 了解当前任务的目标、范围、验收标准 |
| 2 | `agentforge-spec-v0.1.md` | 领取任务后 | 了解相关模块的技术规格和约束 |
| 3 | 当前任务的**涉及文件** | 开始编码前 | 了解现有代码，避免覆盖 |
| 4 | 依赖任务的**涉及文件** | 修改公共接口前 | 确保不破坏已完成的功能 |

### 读取规则
- 不要一次性读取所有文档，按需读取
- 读取文件时关注**接口定义**和**类型签名**，不要逐行理解实现细节
- 如果规格文档和已有代码冲突，以规格文档为准（见第 6 节）

## 2. 如何领取任务

### 领取流程

```
1. 读取 task-backlog-v0.1.md
2. 找到当前 P 阶段中第一个状态为 pending 的任务
3. 检查该任务的依赖任务是否全部完成
4. 如果依赖未完成 → 跳过该任务，找下一个无依赖的 pending 任务
5. 如果所有 pending 任务都有未完成的依赖 → 报告阻塞
6. 选中任务 → 开始执行
```

### 任务状态

| 状态 | 含义 |
|------|------|
| pending | 未开始 |
| in-progress | 正在进行 |
| done | 已完成并通过验收 |
| blocked | 依赖未完成，暂时无法开始 |

### 更新任务状态
- 开始任务时：将状态改为 `in-progress`
- 完成任务时：将状态改为 `done`

## 3. 如何判断任务完成

### 自检清单

每个任务完成后，AI 必须逐项检查该任务的**验收标准**：

1. **代码层面**：所有涉及文件已创建/修改，无 TypeScript 编译错误
2. **类型层面**：所有新增接口有 TypeScript 类型定义，无 `any` 类型
3. **IPC 层面**：新增的 IPC channel 在 preload 中已暴露
4. **Store 层面**：新增的 Store action 可正常调用
5. **功能层面**：任务描述中的验收标准全部满足

### 验证方式
- **P1 任务**：修改后能 `pnpm dev` 启动无报错即视为通过
- **P2/P3 任务**：手动模拟场景验证或运行 vitest 单元测试
- **集成验证任务**：按该任务的验收标准执行端到端验证

### 未通过处理
- 如果自检发现未满足的验收标准 → 修复后重新检查
- 如果 3 次修复仍未通过 → 报告阻塞，说明具体问题

## 4. 完成后需要更新的文件

### 每个任务完成后必须更新

| 文件 | 更新内容 |
|------|---------|
| `task-backlog-v0.1.md` | 将任务状态从 pending/in-progress 改为 done |

### 以下情况需要额外更新

| 场景 | 额外更新 |
|------|---------|
| 新增了 IPC channel | 更新 `agentforge-spec-v0.1.md` 第 7 节的 Channel 表 |
| 新增了数据表 | 更新 `agentforge-spec-v0.1.md` 第 6 节的建表 SQL |
| 修改了接口签名 | 更新 `agentforge-spec-v0.1.md` 对应章节 |
| 新增了错误码 | 更新 `agentforge-spec-v0.1.md` 第 14 节的错误码表 |
| 新增了文件/目录 | 更新 `agentforge-spec-v0.1.md` 第 3 节的目录结构 |
| P 阶段最后一个集成验证任务完成 | 在 `task-backlog-v0.1.md` 中标记该阶段完成 |

### 更新原则
- **只追加或修改已有条目，不删除**（规格文档是累积的）
- 更新时在修改处加注释 `<!-- Updated in TASK-XX -->`

## 5. 遇到规格冲突时如何处理

### 优先级

```
任务 Backlog (具体要求) > 规格说明书 (技术规格) > 已有代码 (实现)
```

### 冲突场景

| 场景 | 处理方式 |
|------|---------|
| Backlog 说的和 Spec 不一致 | 以 Backlog 为准，同时更新 Spec |
| 已有代码和 Spec 不一致 | 以 Spec 为准，修改代码 |
| 已有代码和 Backlog 不一致 | 以 Backlog 为准，修改代码 |
| Spec 中两个章节矛盾 | 以更具体的章节为准，或在 Spec 中加注释澄清 |
| 任务需要的接口 Spec 中没有定义 | 先在 Spec 中补充接口定义，再实现 |

### 报告机制
- 发现规格矛盾 → 在完成任务时一并提出，建议修改方案
- 不要自行决定架构方向变更

## 6. 不能随意修改的文件

### 高风险文件（修改需特别谨慎）

| 文件 | 原因 | 修改规则 |
|------|------|---------|
| `src/shared/types.ts` | 所有进程共享的类型定义 | 只能追加新类型，不能修改已有类型的字段名或删除字段 |
| `src/preload/index.ts` | 进程间通信的唯一桥梁 | 新增 IPC channel 必须同步在此暴露和类型定义 |
| `src/main/db/schema.sql` | 数据库 schema | 只能追加新表/新列，不能删除或重命名已有列 |
| `src/main/index.ts` | 应用入口 | 只在任务明确要求时修改 |
| `electron.vite.config.ts` | 构建配置 | 只在任务明确要求时修改 |
| `package.json` | 依赖管理 | 安装新依赖时修改，不随意删除已有依赖 |

### 中等风险文件

| 文件 | 修改规则 |
|------|---------|
| 已完成任务的涉及文件 | 修改前确认不影响已有验收标准 |
| Store 文件 | 新增 action/computed 可以，不修改已有 action 的行为 |
| 组件 Props | 只能追加可选 Props，不能修改或删除已有 Props |

## 7. 必须遵守的安全规则

### 绝对禁止

1. **不提交 API Key**：代码中不得硬编码任何 API Key，包括占位符 `
2. **不使用 `any` 类型**：所有函数参数和返回值必须显式类型标注 
3. **不绕过 preload**：渲染进程不直接使用 `require('electron')` 或 Node.js 模块
4. **不执行未经验证的命令**：Agent 工具执行的文件操作必须限制在用户指定范围内
5. **不将用户数据发送到外部**：除用户主动调用的 LLM API 外，不得向第三方发送数据

### 必须遵守

1. **IPC 类型安全**：preload 中每个暴露的方法必须有 TypeScript 类型
2. **输入校验**：IPC handler 必须校验必要参数是否存在且类型正确
3. **错误不静默**：所有 async 函数必须有 try/catch，错误必须上报到渲染进程
4. **SQL 参数化**：所有 SQL 查询必须使用参数化查询（`?` 占位符），禁止字符串拼接
5. **依赖最小化**：安装新 npm 包前确认是否真的需要，优先使用已有依赖
6. **单文件组件**：Vue 组件必须使用 `<script setup lang="ts">` 语法
7. **命名规范**：严格按照 Spec 第 13 节的命名规范

### 文件修改原则

1. **修改前先 Read**：每次修改文件前必须先读取最新内容
2. **小步提交**：每个任务完成后确保应用能正常启动
3. **不引入无用文件**：不创建空文件占位，不创建不会被引用的文件
4. **不复制粘贴大段代码**：如果发现多文件有重复逻辑，提取为公共模块

## 8. 开发节奏建议

### 单次开发会话

```
1. 领取 1 个任务
2. 读取相关文档和涉及文件
3. 实现功能
4. 自检验收标准
5. 更新任务状态和相关文档
6. 停止，等待下一个指令
```

### 不要做的事
- 不要一次领取多个任务（除非它们完全独立且很小）
- 不要跨阶段开发（P1 未完成不要做 P2 的任务）
- 不要跳过集成验证任务
- 不要在没有读取规格的情况下实现功能
- 不要在任务完成后继续"优化"或"改进"代码
